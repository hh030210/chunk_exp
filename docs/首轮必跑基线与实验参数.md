# 首轮切片交付与评测对接说明

更新日期：2026-11-09  

## 1. 首轮基线与共同数据

B0–B5 都使用下表所列的同一批数据文档和同一份评测 query 清单。每种方法各自切分同一文档集合；不要按 query 分别生成不同版本的文档切片。

| ID | 基线 | 切片阶段所需模型 |
|---|---|---|
| B0 | 固定长度切分 | 无；按 token 长度切 |
| B1 | 递归结构切分（标题→段落→句子） | 无；按文档结构切 |
| B2 | 语义相似度切分 | Qwen3-Embedding-0.6B 计算相邻句相似度 |
| B3 | Meta-Chunking | 本地 Qwen3.5-9B 计算 PPL/margin；普通只返回文本的 API 不够 |
| B4 | PIC / Document Segmentation Matters | Qwen3.5-9B 生成文档摘要；Qwen3-Embedding-0.6B 做语义相似度 |
| B5 | MoC | 必须加载作者的 [MoC router + experts](https://huggingface.co/Robot2050/MoC)；只用 Qwen3.5 重写时另标“MoC 改造版” |

| 数据集 | 要切的文档语料 | 评测 query split | 如何回到原始 query / 文档 |
|---|---|---|---|
| **Natural Questions (NQ)** | 一份固定版本的完整 Wikipedia 检索语料；所有方法使用同一 corpus snapshot、同一 page ID。不要用不同日期的 dump 混跑。 | 当前方案使用公开的 NQ open-domain dev query 文件；固定原始文件、revision 和 SHA-256。 | 保留原始 `example_id`/`id`（如派生文件没有稳定 ID，则用原始文件 SHA + JSONL 行号构造）和 query 原文。用官方 NQ annotation 中的 `document_url` 映射到检索语料的稳定 `wiki_page_id`，把该 ID 写入 `source_doc_ids`；若派生 query 文件没有 annotation 字段，通过 example ID 回查官方原始记录，不要只靠标题字符串连接。[官方数据说明](https://ai.google.com/research/NaturalQuestions/download)、[字段说明](https://github.com/google-research-datasets/natural-questions)。 |
| **CRUD-RAG** | 作者的 `data/80000_docs/` 新闻文档库，保留每条原始文档 ID；使用固定版本的作者语料。 | 使用作者实验文件 `data/crud_split/split_merged.json` 中 `questanswer_1doc` 和 `questanswer_2docs` 的全部记录，分别作为 `author_eval_1doc`、`author_eval_2docs`；不再自行切 train/test，也不 shuffle。loader 按 task key 读取数组，故交付时锁定文件 SHA-256、task key 和原始数组索引。 | 每条 query 用 `CRUD:<task_key>:<raw_array_index>` 定位；样本引用的新闻文档 ID 写入 `source_doc_ids`。作者仓库说明该文件是论文实验使用数据，loader 提供任务数组但不创建随机 test split；CRUD-RAG 结果因此标作作者评测集复现，并做与 MoC 训练数据的重叠检查。[作者仓库与数据文件说明](https://github.com/IAAR-Shanghai/CRUD_RAG)、[官方 loader](https://github.com/IAAR-Shanghai/CRUD_RAG/blob/main/src/datasets/xinhua.py)。 |
| **QASPER** | 官方 `test` split 中所有论文的 `full_text`；同一篇论文只切一次，即使该文有多个问题。 | 官方 `test` split 内的全部 questions；不改写问题，不从 test 中抽样。 | 每篇论文的 `source_doc_id` 使用顶层 `id`；每个 query 的 `query_id` 使用 `<paper_id>:<question_id>`，问题文本使用对应的 `qas.question`。原始 `answers[].answer[].evidence` 保留在原始数据中供我评测；不要把 gold answer/evidence 写进 chunk 文件。[QASPER 数据集卡与字段说明](https://huggingface.co/datasets/allenai/qasper)。 |

> 注意：CRUD-RAG 的 `split_merged.json` 是作者论文实验使用文件，官方 loader 按 task key 读取数组，没有再提供独立的随机 test split。本方案固定使用 `questanswer_1doc` 与 `questanswer_2docs` 全部记录，分别报告；MoC 使用 CRUD 派生训练数据，因此还要做文档级重叠检查，并将有重叠风险的结果标作探索性。

## 2. 评测 query 与 chunk 的对齐规则

核心做法是保留两张小清单：`queries_eval.jsonl` 把评测问题指回原始数据，`documents.jsonl` 把源文档指回原始语料。每个 chunk 带 `source_doc_id` 和原文跨度。这样一个文档即使对应多条 query，也只切一次；评测时用 `query_id` 和 `chunk_id` 记录实际命中关系。

`queries_eval.jsonl` 每行一个问题，至少包含：

```json
{
  "dataset": "QASPER",
  "query_split": "test",
  "query_id": "1909.XXXX:question_3",
  "query_text": "问题原文",
  "raw_locator": {"paper_id": "1909.XXXX", "question_id": "question_3"},
  "source_doc_ids": ["1909.XXXX"],
  "query_text_sha256": "..."
}
```

- `raw_locator` 要足以在锁定版本的原始数据中找到该条问题；数据文件路径、版本和 SHA-256 写入 `config.md`。
- `source_doc_ids` 填原始数据能确认关联的源文档 ID（例如 NQ 标注的 Wikipedia page、CRUD-RAG 样本引用的新闻文档、QASPER 的论文 ID）。如果原始数据没有明确文档关联，填空数组并在 `config.md` 说明，不能猜测。
- 不改写问题，不把 gold answer/evidence 复制进 chunk 文件；评测时我按 `raw_locator` 从原始数据读取 gold。
- 不 shuffle、过滤或重新抽样 query。若必须抽样，先固定 query ID 清单，所有基线共用。`seed=42` 仅用于明确需要随机初始化的算法或获准的抽样。

关联链示例：`query_id → raw_locator → 原始问题/gold`；`query_id → source_doc_ids → source_doc_id → chunk_id`。实际评测的每条检索结果再保存 `{query_id, baseline_id, chunk_id, rank, score}`，因此能从命中的 chunk 回到对应评测问题；同一 chunk 也可以对应多个 query。

ID 固定规则：NQ 优先用官方 `example_id`/`id`，否则用 `NQ:<split>:<原始行号>`；CRUD-RAG 用 `CRUD:<task_key>:<原始数组索引>`；QASPER 用 `<paper_id>:<question_id>`。`source_doc_id` 使用数据集原始稳定 ID；没有原始 ID 时，按相对路径和原始记录索引派生，并把映射写入 `documents.jsonl`。原始文件路径、版本和 SHA-256 写入 `config.md`，行号/数组索引或 paper/question ID 写入每条 query 的 `raw_locator`。

## 3. 切片参数

| 参数 | 要求 |
|---|---|
| tokenizer | `Qwen/Qwen3.5-9B` tokenizer；所有 token 长度都以此 tokenizer 计 |
| 主目标块长 | 512 tokens；B1–B4 尽量让平均块长接近 512，超长 chunk 上限 1,024 tokens；作者方法本身的限制需记录 |
| B0 固定长度 | 主结果：512 tokens、overlap=0；敏感性版本：256 与 1,024 tokens；可加 10% overlap 作为单独版本 |
| B2 阈值 | 只在官方 train/validation 文档上定阈值；不得根据 eval/test query 或 gold answers 调参 |
| B3 | 本地加载 Qwen3.5-9B 获取 PPL/margin；保存模型 revision 与 PPL/margin、动态合并配置 |
| B4 | 每篇文档摘要最多 256 tokens；固定摘要 prompt、Qwen3.5 revision 和相似度阈值 |
| B5 | 使用作者 MoC router/experts；保存下载 revision、文件清单和权重 hash；不自行改训练/路由参数 |
| seed | `42`。确定性切分时注明“seed 不适用”；不允许用 seed 对 eval query 做未经同意的随机抽样 |

每个方法都要切完整的指定 corpus。确实有个别文档解析失败或超过模型输入限制时，不得静默跳过；把 `source_doc_id`、失败原因和采用的处理方式记入 `config.md`。

## 4. Chunk 文件格式

每种方法、每个数据集交付一个 UTF-8 JSONL 文件，一行一个 chunk。chunk 是**文档级**对象，不包含 query ID；query 与文档的关系放在 `queries_eval.jsonl` 的 `source_doc_ids` 中。

```json
{
  "dataset": "QASPER",
  "baseline_id": "B0_fixed_size_512",
  "source_doc_id": "1909.XXXX",
  "chunk_id": "1909.XXXX::chunk_00003",
  "chunk_index": 3,
  "text": "chunk 原文……",
  "start_char": 1200,
  "end_char": 1842,
  "offset_unit": "unicode_codepoint_zero_based_half_open",
  "offset_basis": "normalized_text",
  "source_text_sha256": "...",
  "token_count": 171,
  "source_paragraph_ids": ["section_2:paragraph_4", "section_2:paragraph_5"]
}
```

必需字段：

- `dataset`、`baseline_id`
- `source_doc_id`：严格按上节的 ID 规则，与 `documents.jsonl` 和原始语料对应
- `chunk_id`、`chunk_index`、`text`、`token_count`
- `start_char`、`end_char`、`offset_unit`、`offset_basis`、`source_text_sha256`
- 结构化来源可恢复时填写 `source_paragraph_ids` / section path；QASPER 尤其需要保留 section 与 paragraph 索引，方便将 gold evidence paragraph 与命中 chunk 对齐

偏移量统一为送入 chunker 的**规范化文本**上的 Unicode code point，`start_char` 含起点、`end_char` 不含终点。`source_text_sha256` 是该规范化源文档全文的 SHA-256，`documents.jsonl` 中也记录同一 hash。`config.md` 写清 HTML/JSON/段落如何抽取与规范化，并给出处理代码 commit。不要只交块文本而不交文档 ID 和 span。

`documents.jsonl` 每行一篇源文档，至少保留以下字段，以便从 `source_doc_id` 找回原始语料：

```json
{
  "dataset": "QASPER",
  "source_doc_id": "1909.XXXX",
  "raw_locator": {"paper_id": "1909.XXXX"},
  "title": "论文标题",
  "canonical_url": null,
  "source_text_sha256": "..."
}
```

## 5. 最简交付目录

```text
chunk_handoff/
├── README.md                 # 版本、文件 hash、交接说明
├── NQ/
│   ├── queries_eval.jsonl    # query ID、原文、raw_locator、关联 source_doc_ids
│   ├── documents.jsonl       # source_doc_id 到原始文档位置、URL/title、文本 hash 的映射
│   ├── config.md             # NQ 语料版本、解析、seed、B0–B5 参数
│   └── chunks/
│       ├── B0_fixed_512_o0.jsonl
│       ├── B0_fixed_256_o0.jsonl
│       ├── B0_fixed_1024_o0.jsonl
│       ├── B1_recursive.jsonl
│       ├── B2_semantic.jsonl
│       ├── B3_meta_chunking.jsonl
│       ├── B4_PIC.jsonl
│       └── B5_MoC.jsonl
├── CRUD-RAG/                 # 同样包含 queries_eval.jsonl、documents.jsonl、config.md 和 B0–B5 chunks
└── QASPER/                   # 同样包含 queries_eval.jsonl、documents.jsonl、config.md 和 B0–B5 chunks
```

只交切片、原始 ID/文档映射、query 对照清单和配置；不用交 embedding、向量库、retrieval/QA 输出或指标。`config.md` 至少写：原始数据文件及 SHA-256、代码 commit、精确 split/索引范围、模型 ID/revision、tokenizer、chunk 参数、seed、文档规范化流程、解析失败清单。

## 6. 交接检查

- `queries_eval.jsonl` 的每条记录都能按 `raw_locator` 在指定原始文件中找到，问题文本 hash 一致，query ID 唯一；`source_doc_ids` 能映射到 `documents.jsonl`。
- NQ 的 Wikipedia snapshot/page ID 映射固定；CRUD-RAG 的 task key、原数组索引、新闻文档 ID 固定；QASPER 的 `<paper_id>:<question_id>` 可回到原记录。
- B0–B5 使用同一份 `documents.jsonl`、同一套评测 query；任何遗漏文档都在 `config.md` 列明。
- 每个 chunk 都可由 `source_doc_id + source_text_sha256 + span` 回到确切源文本；QASPER chunk 还可回到 section/paragraph。
- 我端导入 chunks 后，按 `query_id` 从原始 query 文件取问题；retrieval 输出保存 `query_id` 与命中的 `chunk_id`。这保证后续换检索器、生成模型或指标时，仍能回到同一条原始评测 query 和 gold evidence。
